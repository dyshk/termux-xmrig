Xray + VLESS Reality 生产部署完整检查清单

回答：截图里的 config.json 只是核心配置骨架，不能直接当唯一步骤｜生成时间：2026-09-27
先说结论：截图里的配置只是让 Xray 能“听懂”你要开什么协议的核心骨架。真正让节点跑起来，还需要：安装 Xray 程序 → 生成 UUID 和 x25519 密钥对 → 把注释去掉写成合法 JSON → 放通防火墙 443 → 启动 systemd 服务 → 客户端填对参数。下面按顺序列出完整清单。

一、原截图配置存在的 4 个直接问题

问题说明修正方式
JSON 里含注释标准 JSON 不支持 // 注释；Xray 使用 Go 标准 json 库，带注释会启动失败删除所有 // ... 注释，或使用 JSON 验证器检查
UUID/私钥是占位符"你的UUID"、"你的私钥" 不是有效值，必须替换为真实生成的字符串用 xray uuid 和 xray x25519 生成
没有日志配置默认无日志，出错时无法排查；生产建议开启 error log加 log 字段
端口未说明防火墙只写 "port": 443，但系统防火墙/云安全组没放行 443 的话，外部连不上放行 443/tcp，并确认云厂商安全组也放行

二、完整部署清单（按顺序打勾）

Step 0：准备

拥有一台 Linux VPS（建议 Debian 12 / Ubuntu 22.04，KVM 虚拟化）
确认云厂商安全组 / 防火墙已放行 TCP 443（以及你用的 SSH 端口）
已通过 SSH 登录到 root 用户

Step 1：系统初始化（提升稳定性）

apt update && apt upgrade -y
apt install -y curl wget socat ufw vim

# 开启 BBR（推荐，明显改善吞吐）
echo "net.core.default_qdisc=fq" >> /etc/sysctl.conf
echo "net.ipv4.tcp_congestion_control=bbr" >> /etc/sysctl.conf
sysctl -p

# 检查 BBR 是否生效
sysctl net.ipv4.tcp_congestion_control   # 应显示 bbr

Step 2：安装 Xray-core

# 官方安装脚本，自动配置 systemd 服务
bash -c "$(curl -L https://github.com/XTLS/Xray-install/raw/main/install-release.sh)" @ install

# 验证安装
xray version
systemctl status xray
注意：如果手动安装（不用官方脚本），你还需要自己写 systemd service 文件、创建 /usr/local/etc/xray/config.json 目录权限。官方脚本省心，推荐直接用。

Step 3：生成身份凭据

xray uuid       # 生成 UUID，客户端“用户 ID”填这个
xray x25519     # 生成 PrivateKey（服务端用）和 PublicKey（客户端用），务必保存好

Step 4：写入合法的生产配置

下面是去掉注释、可直接使用的配置模板，仅需替换 3 处：

  • YOUR-UUID-HERE → Step 3 生成的 UUID
  • YOUR-PRIVATE-KEY-HERE → Step 3 生成的 PrivateKey
  • 伪装目标 dest 和 serverNames 可保留 www.microsoft.com:443，也可换成其他真实、TLS1.3、流量大的大站
cat > /usr/local/etc/xray/config.json <<'EOF'
{
  "log": {
    "access": "/var/log/xray/access.log",
    "error": "/var/log/xray/error.log",
    "loglevel": "warning"
  },
  "inbounds": [{
    "port": 443,
    "protocol": "vless",
    "settings": {
      "clients": [
        {
          "id": "YOUR-UUID-HERE",
          "flow": "xtls-rprx-vision"
        }
      ],
      "decryption": "none"
    },
    "streamSettings": {
      "network": "tcp",
      "security": "reality",
      "realitySettings": {
        "dest": "www.microsoft.com:443",
        "serverNames": ["www.microsoft.com"],
        "privateKey": "YOUR-PRIVATE-KEY-HERE",
        "shortIds": [""]
      }
    },
    "sniffing": {
      "enabled": true,
      "destOverride": ["http", "tls", "quic"]
    }
  }],
  "outbounds": [
    { "protocol": "freedom" }
  ]
}
EOF
shortIds 建议：当前模板用空串 "" 表示任意 shortId 都接受。为减少被扫描误触，可改成随机 2 位十六进制，例如 "shortIds": ["a1", "3f", "9b"]，客户端 link 里也要带对应 sid。

Step 5：防火墙放行

ufw allow 22/tcp    # SSH 端口，按需改
ufw allow 443/tcp
ufw enable
ufw status

Step 6：启动并验证

systemctl restart xray
systemctl enable xray          # 开机自启
systemctl status xray          # 应显示 active (running)
journalctl -u xray -f          # 实时看日志

启动后，如果 error.log 为空、status 为 active，说明服务端已就绪。

Step 7：生成客户端分享链接

把下面字符串里的 4 个占位符替换为你的真实值：

vless://YOUR-UUID-HERE@你的服务器IP:443?encryption=none&flow=xtls-rprx-vision
  &security=reality&sni=www.microsoft.com&fp=chrome
  &pbk=YOUR-PUBLIC-KEY-HERE&sid=&type=tcp#我的Reality节点

说明：

  • sni 必须和 serverNames 里的值一致（即伪装目标域名）
  • pbk 填 Step 3 生成的 PublicKey
  • sid 如果 shortIds 用了空串就留空；如果用了 "a1" 就填 &sid=a1
  • fp=chrome 是 TLS 指纹，主流客户端都支持

四、常见启动失败原因速查

现象最可能原因处理
systemctl status xray 失败config.json 含注释或 JSON 语法错误用 python3 -m json.tool /usr/local/etc/xray/config.json 验证；删除注释
端口被占用443 被 nginx/caddy 占用停掉其他服务，或改 Xray 端口并放行
外部连不上 443云厂商安全组 / ufw 没放行双重检查安全组和 ufw
客户端提示 auth failedUUID 填错，或 flow 不匹配服务端和客户端 UUID、flow 必须完全一致
Reality 握手失败sni 和 serverNames 不一致，或 pbk 填错重新核对 PublicKey/PrivateKey 是否来自同一对 x25519

五、关于“只有这些代码够不够”的最终回答

不够，但也“核心”。

那张截图里的 config.json 是唯一不可替代的配置核心——它定义了协议、端口、加密参数、伪装目标。但让这份配置真正产生作用，还需要：

  • Xray 程序本体（安装）
  • UUID 和 x25519 密钥（身份）
  • 合法的 JSON 格式（去掉注释）
  • 防火墙/安全组放行（网络可达）
  • systemd 启动服务（长期运行）
  • 客户端参数对应（最后一步）

缺少任意一环，服务端都不会“自动”工作。按本清单顺序执行即可。
